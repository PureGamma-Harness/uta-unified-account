# Batch execution-disposition validation delivery

Recovery must reject audit claims that cannot be emitted by the batch executor. For membership `[A,B,C]`, completed execution `[A,C]` is valid when B is skipped; `[C,A]` is invalid. A previously quarantined command may remain in the member snapshot, but the batch cannot claim that it executed that quarantine. Newly executed commands have only SUCCEEDED or REJECTED business outcomes.

The delivery preserves writer-recovery base `6010e920a168b35fccfc9ef9ee34e030b28b11d9` and incorporates runtime repair `ff07673fcecfd25fa7df9aa212a710801142a799`. Only `uta/durable_batches.py` changes at runtime: ordered-subsequence validation and executed-state validation. Selection, FIFO, fencing, ledger effects, command IDs, HTTP errors, schema and persisted format retain their existing contracts. This does not establish that an impossible disposition or financial loss occurred in an existing authority.

## Evidence and acceptance

The baseline's first eight synthetic cases retained six controls and two RED counterexamples. The repair's first five methods covered 26 subcases and passed. Independent `7d650309618c7d5d3bed11bd5d9ec4ca84b9ea09` verified the reachable business states and ran eight new methods / 1,694 bounded checks successfully. All first streams and source pins remain retained; no previous result was rerun or overwritten.

Those runs evaluated the actual selected method AST with synthetic data. They do not exercise UTA module import, SQLite, native fencing, real recovery, performance or the complete integrated tree. The method, canonical helper and terminal-definition source blobs match the reviewed inputs after integration with base6010. Whole-suite CI for this new delivery remains a separate gate. No production, financial or real-funds approval is granted.

## Deployment and compatibility

This candidate is for a new isolated synthetic layout under its pinned artifact. An existing code-bound authority must retain its matching artifact and history; no forward financial-code migration or in-place production upgrade is supplied by this patch. Public borrowing/product/mode enablement does not change.

Valid dispositions generated by the reviewed executor remain valid. An impossible historical record now makes history verification/recovery fail closed. Preserve the original immutable manifest, outcome, commands and evidence for investigation; do not rewrite its execution list or change original business IDs. Disable new admission and retain pending recovery obligations. There is no automatic data repair.

## Rollback and recovery

Before activation, discard the unused synthetic candidate and retain the original artifact. After any confirmed commands, halt new work, query every original command ID and reconcile under the authority's matching artifact. Do not erase an outcome, restore an older snapshot over confirmed trades, or bypass source binding by substituting another binary. Disabling new batch selection does not remove existing manifest recovery obligations. Reverting the narrower validator weakens protection and cannot certify a rejected record. A production upgrade/rollback procedure requires its separately implemented and accepted migration protocol.
