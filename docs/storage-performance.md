# 持久化连接路径实验与否决结论

## 结论与上线边界

本轮没有证明应合入连接生命周期优化。三组同配置短测，独立事务连接的平均唯一持久接纳率为约 **362.2/s**，保留 idle WAL keeper 为约 **373.7/s**；差异约 3.2%，配对收益范围 0.3%–6.0%，服务端 P99 没有稳定改善。该差异不足以抵偿额外资源和 fork 生命周期的复杂性，**本交付只保留证据，不合入 keeper 运行代码**。正式数据库仍每事务使用独立连接。

实验代码单独保留在工程分支 `perf/connection-path@5a97d24`，最终接口要求显式 opt-in、默认关闭；下文描述其测试约束，不表示这些实验接口已经进入主交付。每次测量还附有匹配该次哈希的实验源码压缩件，避免依赖分支长期存在。

所有测试仍使用 WAL、`synchronous=FULL`、事务前 `BEGIN IMMEDIATE`、原有精确账本和幂等记录。没有改为异步确认、NORMAL 同步、内存存储或在 COMMIT 前返回成功。10,000/s、30 分钟、完整撮合清算和多节点验收全部仍未通过。

## 观察与实验设计

原 profile 显示大量时间处于 SQLite `execute`、COMMIT 和连接路径。`execute` 时间包含锁等待和 SQLite I/O，不能直接等同于 SQL CPU 时间；cProfile 自身也有开销。最后一个 WAL 连接关闭可能引起检查点和文件收尾，因此单独测试保留一条只查询的 idle connection，业务事务仍各自打开和关闭独立连接。

配对实验依次为 before-1、after-1、before-2、after-2、before-3、after-3。before 使用 `0bdf9b3`；after 使用实验代码 `51a4423`。提交 SHA、实际模块 SHA-256、生成器哈希、平台、CPU quota、磁盘、SQLite 和全部配置在每次 environment/summary 中。为避免后续默认值变化使实验不可复现，每次同时保存了 `storage-source.py.gz`，其哈希与该次 environment 匹配。

每组均为开放环 5 秒、每秒计划到达 1000、2 worker、1 shard、20 accounts、1024 队列、1000ms 软 deadline、最多 10 秒排空、启用 cProfile。每条任务包含一次持久接单和另一次本地撤单，两个事务的时间都计入。吞吐分母包含排空时间，拒绝与队列满不计为接纳。该工作负载没有撮合、成交或资金/仓位结算，不能用作清算成交吞吐。

三次 keeper 服务端 P99 分别约 82.47/82.22/82.14ms；独立连接约 82.22/81.97/56.63ms。延迟尾部并未稳定改善。全部六次均有过载或软 deadline 超限，正式容量 gate 为 false；未发生技术失败、结果未知或重复结果。共享工程主机的 5 秒诊断不能替代专属硬件的长稳统计。

原始 30,000 个计划到达记录、精确纳秒时间、每次 summary/environment、压缩 cProfile、文本 profile、源码与 SHA-256 manifest 保存在 [实验目录](../benchmarks/results/20261114-wal-lifetime/)。`comparison.json` 保存机器可读对照和未批准结论。不得只引用均值而省略失败 gate、队列等待或拒绝量。

## 实验分支接口及资源约束

以下代码仅适用于独立实验分支，当前主交付没有 `keep_wal_open` 参数，不应直接复制到部署配置。

```python
from uta.storage import Database

with Database("/private-state/exchange.sqlite3", keep_wal_open=True) as database:
    with database.transaction() as connection:
        # 每个命令仍使用独立、FULL 同步的事务连接。
        pass
```

keeper 不执行应用事务，设置 query-only，并且不持有跨命令的读事务。实例只持有一条 keeper，弱引用 finalizer 是兜底；服务关闭顺序应先停止准入、等待在途事务，再 `database.close()`。`close()` 不强行回滚已准入事务，之后的新事务明确拒绝。不得创建无限数量的长生命周期 Database 实例。

文件权限每次连接都重新检查；同一实例打开后若数据库 inode 变化或文件消失，拒绝操作，不静默创建新权威。持久状态应始终在服务用户控制的私有目录。对于外部直接传入连接，仍检查其有活动事务且属于该数据库。

fork 子进程会丢弃继承的 idle keeper 并重置其 Python 锁，下次事务建立自己的 SQLite 连接。只支持在没有进行 SQLite 操作/事务时 fork；不要在另一个线程执行 SQLite 时 fork，这也是 SQLite 本身的边界。工作进程优先使用 spawn。新增测试验证父子各自连接、父进程仍可继续提交，并没有把测试扩展为任意多线程 fork 安全承诺。

## 正确性验证

实验分支 9 项测试检查默认关闭、query-only、独立事务连接、WAL/FULL/外键不变、显式关闭、GC 资源释放、并发线程、fork、权限/文件替换和删除拒绝，以及原始证据完整性。在实验分支执行的 251 项完整回归覆盖真实 SQLITE_FULL、数据库忙、提交前/后进程退出、响应丢失、双侧结算回滚、网关及 SIGTERM drain；日志见实验目录中的 `regression.txt.gz`。这些数量不冒充后续集成主分支的最终测试数。证据交付另含独立校验测试，核对六次结果的哈希、唯一到达和否决 gate。

此优化没有 schema 变化。回滚时保留数据、关闭实例，删除 `keep_wal_open=True`，重新打开同一个数据库；不回退账本、命令 ID 或已确认成交。数据损坏/对账失败按恢复手册处理，不能通过自动换空数据库恢复服务。

## 后续应优先验证的结构性优化

1. 单分片账户命令由有界单写入者队列串行化，避免多个连接争锁和忙等待；撤单、还款和清算使用保留容量。必须仍在读风险前取得权威写锁。
2. 在同一 FULL 事务中分组处理命令，逐命令保存幂等和接纳回执，仅在组 COMMIT 成功后发布确认。任何命令的业务拒绝必须保留其他命令的隔离和完整事务恢复；需要独立故障及形式化验证，当前未实现。
3. 不变市场/规则解析结果按版本缓存，保留不可变输入和源码/数据版本，先与精确参考计算差分。避免把大额账本重放放入正常请求路径。
4. 实测多个独立账户分片和真实双侧撮合的端到端瓶颈，再设计跨分片成交义务与恢复。多个 SQLite 文件的局部高吞吐不能证明跨分片交易已经生产可用。

这些是待实施和待验收的建议，不是本实验已经提供的性能保证。
