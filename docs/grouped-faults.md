# Grouped admission 的独立故障验收

本报告只覆盖标准库实现的本地交易接纳/撤单批提交。资金和价格均为合成数据，不接入外部撮合、托管或真实账户。分片、复制确认、跨 AZ 容灾、完整 PM、10,000/s 与 30 分钟门槛不由这些小样本测试授予。

## 独立测试原则

故障组不修改 `uta/admission.py`，不复用新的实现来生成预期金融结果。观察对象包括 Future、账户版本/保证金、持久订单、账本、outbox 和重新打开后的相同业务 ID。两笔 1 单位、100 USD 限价、10% IM、0.04% 费率的独立预期占用是 `2 × (100 × .1 + .04) = 20.08 USD`；挂单不能改变现金或产生额外结算分录。

测试实际执行 SQLite 事务、子进程和线程。没有用 mock 成功回执、skip 或手写假账替代故障验证。为确定形成同一组，使用有上界的收集窗口和固定批长，并核对 `committed_batches`。

| 编号 | 真实故障/竞争 | 必须观察到的行为 |
| --- | --- | --- |
| GA-F001 | 在管理器即将调用 SQLite COMMIT 前，用事件暂停实际事务 | 同组成功 Future 与排队业务拒绝 Future 均未完成，另一个只读连接仍看不到订单；释放后一次提交并占用 20.08 |
| GA-F002 | `defer_foreign_keys=ON`，成功改完订单后插入未满足的外键，SQLite 在真正 COMMIT 时拒绝 | 所有 Future 为技术批失败，不能先发成功；账户/订单/分录/事件/故障行全部回滚，已确认批计数为零 |
| GA-F003 | 第二命令已写订单和事件后抛 SQLite OperationalError | 包括早先有效命令在内整组回滚，均不能返回业务成功 |
| GA-F004 | 第二账户的 materialized ledger 整数损坏，底层错误被服务封装成 HTTP 409 | 仍是整批技术失败，不能把账本损坏当普通业务拒绝后提交其他命令 |
| GA-F005 | 两个合法单之间插入保证金不足单 | 只回滚被拒命令的 savepoint，合法单在同一次外层提交成功；没有给拒绝 ID 建单或生成额外资金 |
| GA-F006 | 同一组中市场过期的新单与不依赖新鲜价格的撤单 | 新单返回 market_unavailable 503；撤单照常耐久提交并释放真实占用，不将市场不可用计为成功或普通保证金拒绝 |
| GA-F007 | 用 `PRAGMA max_page_count` 限制真实数据库增长，循环写组直到 SQLite 返回 FULL | 完整异常链保留真实 SQLITE_FULL；失败批完全无变化，恢复容量并重开后同 ID 可执行一次且重试不重复占用 |
| GA-F008 | 1 个命令正在事务中，队列满、排队 Future 取消、同时 close | 运行中 Future 不能由 cancel 撤销金融影响；尚未运行 Future 可取消；新请求过载快拒；close 等在途提交完成，取消项不建单 |
| GA-F009 | 子进程在第二命令中、COMMIT 前、COMMIT 后但回执前 `os._exit`，以及输出回执后退出 | 未提交组重开全回滚；已提交/响应丢失组仍恰好两单；原 ID 重试后事件、预占及数量完全不变 |
| GA-F010 | 数据库已经真实 COMMIT，但事务封装的返回路径随后报错 | Future 只能报技术失败/结果未知，不能保证“没有提交”；从数据库查到两单，原 ID 查询/重试收敛且不新增影响 |
| GA-F011 | 一个已成功 Future 的回调递归提交/关闭同 worker，并抛 SystemExit | 重入被快速拒绝、self-close 不死锁、回调异常被隔离；同批另一个已经提交的回执仍能完成 |

GA-F007 是真实 SQLite 容量上限错误，不是把宿主磁盘填满，也不证明任意文件系统 I/O 或断电行为。GA-F002 的延迟外键确实由 SQLite COMMIT 失败，不以提前抛 Python 异常冒充落盘失败。GA-F003/010 是显式 Python 包装层故障注入，各自检查不同的持久状态，不能混称为物理故障。

## 失败、未知与重试

排队成功只表示系统受理了本机内存中的待处理工作，不是持久接纳。有效回执以外层 WAL/FULL COMMIT 返回为边界；排队取消和队列满没有金融影响。

在提交响应丢失、进程退出或包装层报错时，调用者可能无法从异常判断提交与否。技术批失败信息不能承诺“全部没提交”。客户端保留原账户/订单 ID 和原始内容，查询原订单或重试相同 ID；换新 ID 会把未知结果变成可能重复业务。全组的 API 请求仍是若干独立命令，不是客户多腿原子金融指令。

正常业务拒绝回滚一个 savepoint；SQL/FULL、存储损坏、配置损坏和未分类内部错误停止整个组。必须检查异常链，不能因外层 409 或普通 ValueError 字样把内部存储问题误分成业务拒绝。过期市场与取消的共存场景按操作安全条件分别处置。

## 执行与局限

```sh
python -m unittest discover -s tests -p test_admission_faults.py -v
```

该脚本不依赖第三方服务或真实密钥。测试时应使用最终实现提交；最终独立运行结果、前置实现 SHA 和执行时间由交付记录保留。没有跳过不通过场景来获得通过数。

2026-11-14 首次不可变实现验收基线为 `32c2014`（本独立 worktree 的依赖 cherry-pick 为 `d9bdbde`，运行文件内容相同）。**11 项独立故障测试通过，0 failures/errors/skips，约 2.0 秒**；另复跑实现组的 14 项测试全部通过，约 2.3 秒。执行时间只证明小样本已运行，不是吞吐、P99 或生产恢复时限。后续实现增量需按最终集成提交重新验收，不能自动引用该版本结果。

这组证据不证明网络分区、复制水位、旧主 fencing、任意机器掉电后的 RPO、公开 API 的签名/nonce 或实际撮合吞吐。故障注入发生在定义的事务和进程边界。生产金融和容量关卡仍保持 BLOCKED，独立组没有签发真实资金或 HA 启用批准。
