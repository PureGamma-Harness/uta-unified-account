# 持久命令、单写者与恢复的独立验证

独立验证组只使用合成资金、账户、行情与故障。本报告区分参考账本、研究 Store、持久交易服务与独立进程协议的证据。参考模型通过不等于持久金融实现通过，排队成功也不等于订单已接纳。生产、真实资金、复制/HA与正式容量关卡继续 **BLOCKED**。

## 阶段一：独立发现并关闭宽精度回放缺口

以 `ad3f5b8` 为基线，本组实际复现：`Ledger({'USD':18}, unit_digits=60)` 可以记入金额 `10000000000000000000000000.123456789012345678`，而 `Ledger.replay` 强制恢复为默认38位，因而拒绝这份合法日志；接口还不允许调用方传回原 `unit_digits`。这是内存研究账本的恢复参数缺口，不是持久交易账本范围已被扩大。

修复来自远端 `fix/ledger-replay-precision` 的 `a85567a`，集成负责人只挑选四文件的小补丁为 `2bddc9a`，没有合并旧分支快照。回放现在接受显式保留的原精度，默认38位和构造器范围校验继续保留。历史金额不能自动放宽恢复政策。

`tests/test_durable_reference.py` 的独立回归不调用生产换算或风险函数生成预期，按整数最小单位及 `Fraction` 核对：

- 原精度38/40/60、USD精度18，接近各自上限的资金、1个最小单位付款和精确余额。
- `prec=1`、Emax/Emin=±2、Inexact/Rounded traps 下回放、原ID重试及随后越界记账拒绝；拒绝不改变分录与余额。
- 默认精度仍拒绝宽历史，非法显式精度仍由原构造器拒绝。

基线原始测试产生9个子案例 TypeError（缺 `unit_digits` 参数），默认拒绝宽历史的测试通过；没有跳过失败或改金融预期。应用 `2bddc9a` 后，本阶段三个精度测试及下述模型回归 **4项全过、0 failures/errors/skips，0.014秒**，Python3.12.14。最终金融与进程候选就绪后再补全本文件的实际验收记录，不能把这4项小范围结果冒称完整持久命令验收。

## 研究 Store 提交失败分支的只读审查

只审查了 `ad3f5b8` 之外真正新增的提交 `origin/test/store-commit-recovery@c57176b`。该分支与基线共同祖先为旧 `02549e5`，因此不能用两端完整快照差异恢复旧文件。实际补丁仅新增 `tests/test_store_commit.py` 和两处文档更新，没有运行时修改。

三个新案例在真实 SQLite 建立 `DEFERRABLE INITIALLY DEFERRED` 外键；触发器先成功写入，最后由真实 COMMIT 失败。trace 回调只观察真实SQL，不伪造 COMMIT 异常或金融成功。分别验证单命令、同库多账户批次、独立分片部分成功后原ID恢复；成功分片的 transition 不得再次执行。独立组通过 `git show` 在内存载入该测试源码，在当前基线实际执行 **3/3通过、0跳过，0.112秒**，没有引入分支文件或覆盖当前文档。

未发现测试质量上的挑选阻断。建议只引入新增测试文件，并围绕当前版本更新说明。它们验证 `uta.store` 的研究快照与回执协议，不等同于 `ExchangeService` 交易账本、持久inbox、fencing或撮合验收；持久路径需要各自独立故障证据。

## 阶段二：实际持久队列与写者隔离

依赖实现 `39157ad`、`c05e10f`、`1423758`、`a057362` 后，本组只新增测试，没有修改生产函数。三项精度、一项模型、九项队列和五项租约测试共 **18/18全过、0 failures/errors/skips，1.312秒**；增加FIFO负控制后再次完整执行，仍18项全过，1.632秒，Python3.12.14。实现组自己的测试数不合入此独立计数。

| 实际场景 | 独立观察与预期 |
| --- | --- |
| 已确认持久排队、服务重建 | `durably_queued/PENDING` 时没有订单、预占、分录、账户版本或金融事件；重建QueueStore与服务后仍有同一排队记录，只有执行成功COMMIT后才出现10.04USD预占 |
| 种子16112026、120条命令、三个账户 | 独立Fraction现金书按账户FIFO处理正反向下单、99/100/101价格、重复订单ID、冲突与撤单；逐命令终态、各账户现金/活跃预占/版本及接纳/撤单事件数均一致 |
| 稳定业务拒绝 | 保证金不足形成REJECTED后，即使后来撤单腾出额度，原command ID仍返回原拒绝；只有明确的新command ID才重新判断，未创建金融订单的order ID可以被新决策使用 |
| 原成功回执与当前订单不同 | 数值等价原命令重试不重复；不同payload或kind冲突；后来撤单后原命令仍返回其原OPEN回执，而当前订单为CANCELLED，不把当前投影写回历史终态 |
| 入队时行情有效、执行时过期 | 入队不锁定旧行情资格；执行时拒绝market_unavailable/503，金融表不变；行情恢复不复活原REJECTED，明确新命令才可接纳 |
| 写后预期业务拒绝 | 测试在已尝试写order/version/event后抛已声明insufficient_margin；金融savepoint全部回滚，拒绝终态独立持久，原资金不变 |
| 真实COMMIT后回执通道异常 | Python包装在真正COMMIT返回后抛错；原command已SUCCEEDED；record_failure不得将成功改为失败或隔离，服务重建与原ID重试不新增资金影响 |
| 技术退避与队头 | 技术失败保留PENDING；本账户后续撤单不能越过被退避的队头，其他账户可执行；next_attempt_at等于当前时刻即可重试 |
| 技术重试耗尽 | QUARANTINED保留技术503与不可变记录，无金融订单和资金副作用，不能包装成业务保证金拒绝 |
| 旧服务与新写者 | 在启用managed前已存在且缓存填热的服务，随后deposit/submit/cancel和重新构造均不能写；旧对象仍可只读；当前token写入后只读立即反映新状态 |
| 租约、接管与只读 | 活租约竞争拒绝；read_transaction拒SQL修改；release后旧token不能写；新generation大于旧值，原充值ID只生效一次 |
| 提交前恰好到期 | 同事务已经暂存真实双分录后，将纳秒时钟推进到expires；最终COMMIT拒绝并完整回滚，renew不能复活过期租约 |
| 时钟、boot与最短TTL | 已持久高水位倒退1ns拒写；注入新boot ID需新generation、旧写者失效；.001秒TTL前1ns可写、等号时过期，非法TTL拒绝 |

现金书在固定mark100、IM率.1、费率.0004、USD精度8的政策下独立计算：`abs(q)×max(100,p)/10 + max(0,q×(p−100)) + ceil_1e-8(abs(q)×p/2500)`。预期不调用生产预占、风险、费用或舍入函数，也不把接口返回额用作下一个预期。原命令与金融订单是两套ID：command终态始终保留原结果，当前order投影可以继续改变。

这里的服务重建在同一进程，boot改变为可控输入，并非机器重启或掉电演练；真正独立PID与进程退出故障由另一工作组补充。COMMIT后丢回执案例是明确的包装层故障，不冒充物理磁盘错误。WAL/FULL、可信本机、SQLite原子事务与受控数据库文件仍是前提；同路径恢复旧备份、复制和跨主机fencing未因此得到批准。

当前九项队列测试覆盖的执行kind为首版订单/撤单及已有市场时效语义；不是对所有产品、借贷、外部成交或未来新增kind的通用证明。后续独立PID/router与扩展操作必须以实际候选再验收。当前已验证范围无已确认金融差异或阻断；生产、持续容量与HA关卡继续BLOCKED。

## 阶段三：真实独立PID的额度与回执恢复

在上述依赖上应用 `a175605`，新增一个真实spawn案例：先用明确的离线bootstrap为一个账户入账10.04USD，启动子进程并完成行情/暂停开关屏障，再正常关闭worker。在没有worker时入队，获得`durably_queued/PENDING`，原始SQLite观察仍为零订单及原现金。重建父router对象、启动新worker后，原命令实际执行并预占10.04；第二个相同规模的新命令因容量耗尽被拒绝。

随后实际kill正在持租约的worker，等待另一个真实PID获得更大generation，要求新PID不同于旧PID及测试父PID，且持久owner_pid与新PID一致。成功和拒绝两个command ID在重启后都返回各自原终态。独立SQL核对最终恰有一个订单、一个ORDER_ACCEPTED事件、一个资金入账事件、客户现金为1,004,000,000个USD最小单位，逐币所有科目合计为零；排队和重启未重复冻结或入账。

连同前两阶段，**19/19测试全过、0 failures/errors/skips，2.246秒**。新增测试首次写入时类边界位置错误，导致5个测试fixture AttributeError；这是测试布局错误，修正后完整重跑，没有改金融预期、跳过案例或修改实现。本案包含父router对象重建及真实子进程退出，不宣称已kill整个父进程、机器掉电、跨主机恢复或外部成交恢复。真实双侧撮合/部分清算与物理SQLite故障的候选证据由其他独立工作组提供，本案没有生成或计入成交吞吐。

## 阶段四：持久还款的独立现金流

应用信用共事务helper `7b1e432` 与队列REPAY增量 `ea9b12a` 后，在同一个已fenced的真实服务上新增还款案例。账户原有1BTC，显式资金池借款.1BTC，另记利息.001BTC。先入队还款.0005BTC，确认PENDING时金融表与债务均未变；执行后现金1.0995、应付本金.1、应付利息.0005，证明先息后本。再还.1005后现金为.999、债务为零。

首次还款在`prec=1`、受限指数与舍入traps环境真实执行。此后原还款command ID用等价小数字符串重试仍返回原成功终态，无第三笔还款；新的超债还款命令形成明确repayment_exceeds_debt业务拒绝，金融表不变。SQL独立核对恰有两笔repaid信用回执，USD与BTC各自全部账务科目最小单位合计为零，预期由上述人工现金流给定。

最终本组 **20/20测试全过、0 failures/errors/skips，2.320秒**。这个新增案例覆盖队列与信用同事务，不声称已经在独立PID内验证REPAY路由；进程适配器扩展、还款保留容量的并发故障、长期运行和新增产品仍需各自证据。当前已验证范围没有遗留已确认的金融差异或阻断；该结论不授予生产或真实资金批准。

## 阶段五：managed真实部分清算与worker恢复

`tests/test_managed_liquidation.py` 在 `f238104` 的持久SQL fencing候选上实际执行：两个独立spawn子进程，每个管理自己的分片。离线bootstrap将Victim与Peer明确放在同一片，分别提供1000USD与100000USD；另一片保留123USD的独立账户。金融行为通过持久inbox和真实后台监督/Matcher完成，不使用标记价合成成交、不模拟金融返回、不安装假时钟。

同片实际开仓90@100后，Victim现金为996.4。发布真实当前时间戳的mark90并完成显式激活后，监督器持久冻结账户，新增风险命令被拒且不建单。Peer仅提供45@90真实只减仓对手深度，首笔清算后Victim仍持45，现金544.78。测试等到三个不同的持久后台写入时钟检查点，并持续核对只有两笔总trade、未成交45与现金均不变；没有把空盘口尝试计为成交。

随后真正kill旧worker，要求新PID不同于父PID和旧PID、持久owner_pid相符且generation递增。恢复时原剩余45和已确认trade仍在。重新发布新鲜同价mark90、完成激活，再提供第二张45深度，最终仓位为零并恢复NORMAL。独立现金流为 `1000−3.6−900−3.24=93.16USD`；两笔唯一清算trade均为45@90，未将最初90开仓trade算作清算。两侧共6个fills、系统费用13.68USD、各币账务科目合计为零，冻结拒绝命令没有金融订单。

关闭worker后，用只读Database和原始service/ledger的codec副本运行完整四侧reconciliation，不调用可能修复schema的金融构造器。主片恰有3个实际paired trade/6个fill、零仓位；另一片零订单/零成交/零仓位，独立账户仍为123USD。**首版1/1测试通过、0 failures/errors/skips，1.548秒**。这是单主机合成的部分清算恢复证据，不是跨分片撮合、跨AZ恢复、持续万笔或24小时稳定性验收。Schema3实际透传及required重跑结果见下一阶段。

## 阶段六：required审计下重跑同一真实清算链路

应用审计实现 `dd57cd4`、`9f215b1`、`f97ff31`，以及进程透传 `40faaa6`（依赖takeover `aa309dc`与孤儿owner恢复 `713e676`）后，同一helper分别显式设置 `decision_audit=False` 和 `True`，各自初始化全新的两个分片、运行实际spawn/45+45清算/kill与新generation链路。没有patch父构造器来假装子进程启用了审计。两个模式的所有金融标准数值相同。

required模式要求实际主片schema=3、所有新订单admission_decision_id与全部6笔双侧fill的execution_decision_id非空，持久决策数精确等于订单数加fill数。Victim三次fill分别独立核对：

| fill | 现金前→后 USD | 仓位前→后 | 实现损益 | 费用 | 原始mark/version |
| --- | --- | --- | ---: | ---: | --- |
| 初始开仓 | 1000→996.4 | 0→90 | 0 | 3.6 | 100 / 1 |
| 首笔清算 | 996.4→544.78 | 90→45 | −450 | 1.62 | 90 / 2 |
| 恢复后清算 | 544.78→93.16 | 45→0 | −450 | 1.62 | 90 / 3 |

完成处置后再发布新的当前行情mark110/version4，然后关闭worker。只读查询三个execution decision的原business ID、完整前后现金/仓位、market内容、policy精度/费率与artifact源文件摘要；manifest明确unsigned，不伪造签名。历史numerical replay必须matches且分别得到人工权益：开仓前1000、后996.4；首轮前96.4、后94.78；末轮前94.78、后93.16。这样不会把“复用当前行情”误当历史回放，也没有调用生产函数产生这些预期。

此处replay仅重构历史估值与预占，不能代替当时授权、租约、时效或完整命令再执行的证明。业务拒绝、现货、新借款等尚未审计的范围依实现capability缺口披露；没有补造缺失历史。当前已验证的managed线性部分清算与新决策追溯没有遗留已确认阻断，生产容量、24小时稳定性、跨AZ/复制、完整PM、保险基金/ADL与真实资金审批仍未通过。

## 独立有界命令模型

```sh
python formal/explore_durable_commands.py
python -m unittest discover -s tests -p test_durable_reference.py -v
```

模型不导入任何生产模块。边界为两个账户、四个不可变命令ID、两个写者generation、一个原子数据库写事务。账户容量用整数；命令包括接纳、容量拒绝和撤单。遍历持久排队、按账户先后执行、提交前进程退出、租约过期/接管、终态与金融同提交以及延后投递/查询。已排队记录、金融数据和终态的持久性是模型假设，不是它证明的物理性质。

安全模型实际遍历 **817个可达状态、2372条转换**，没有容量重复占用、同命令重复影响、金融状态缺少成功终态、提前发布接纳、失效写者提交或账户FIFO违反。首版四个负控制后补充FIFO负控制，五个独立变体必须各自产生带动作和状态的反例，否则脚本失败：

| 删除的约束 | 首个反例长度 | 检测的违反 |
| --- | ---: | --- |
| 提交前不得发布接纳 | 4 | 客户收到成功而终态仍为PENDING |
| 金融与终态须同提交 | 4 | 已改变预占但没有成功终态 |
| 原ID重试不得重做影响 | 5 | 同命令产生第二次金融影响 |
| COMMIT须有当前有效写者 | 5 | 已过期或已被接管的写者提交 |
| 同账户须先完成队头 | 5 | 早先命令仍PENDING而后续命令已终结 |

模型不证明实现与抽象等价、任意规模、队列活性/公平性、真实时钟正确、SQLite落盘硬件、跨主机复制或HA。它的成功不能代替独立实际SQL、PID与金融回归。各阶段实际通过范围以上述执行记录为准，未执行范围不提前填写通过结论。
