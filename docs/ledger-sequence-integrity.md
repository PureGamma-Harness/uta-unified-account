# Reference journal sequence integrity

The reference `Ledger.replay` checks that every `JournalEvent.sequence` is a
native Python `int` before checking its consecutive value and calling `post`.
This matches the sequence receipts generated by `Ledger.post`. The previous
value comparison also accepted `True`, `1.0`, `Decimal("1")`, `Fraction(1)`, an
`int` subclass or another object whose equality claimed to match `1`.

For a synthetic USD transfer, the two postings `clearing: -1` and
`customer: +1` with sequence `1` recover a customer balance of USD1. The same
postings with sequence `True` now raise the original `LedgerError` with the
unchanged message `journal sequence is missing or out of order`, before any
posting. No money, precision, asset-scale or journal ordering policy changes.

Four focused methods cover that rejection, consecutive exact two-asset
recovery under a small Decimal context, gaps/ordering/duplicate business IDs,
and native live receipts with idempotent retries. Expected balances are manual
constants; no production calculation generates the expected values. The
negative no-posting observation applies to an invalid first event. A later
invalid event may leave a prefix in the new, unreturned in-memory ledger; this
helper performs no external or persistent write.

## Focused execution contract

`evidence/reviews/ledger-sequence-integrity/once-plan.json` binds the driver,
ledger and four-method fixture by length/SHA. The caller also checks each blob
against the frozen Git commit before execution. The driver compiles only those
retained verified source buffers, not a later filesystem reread. Post-reads are
verification only. Its `source-commit` is an invoker label; Git binding and
actual host exit/reap are caller evidence, not self-attested by this driver.

The caller uses an absolute interpreter with `-I -S -B`, CPU1 and a hard ten
second timeout. The reviewed pure code opens no database, socket, subprocess or
worker thread. Raw stdout/stderr share a 256 KiB reserve-before-write limit with
512 bytes retained for a failure marker. This follows the existing
`19eebff7fe2585bbc153b70529b67b2344da3e0d`/worker-compat RawStream pattern; it is
not an OS sandbox or protection against hostile native writes. A fresh mode0700
output directory and O_EXCL mode0600 files preserve first output. The caller
must preserve the first actual host status, raw bytes, END and input hashes.
Missing evidence or a hard stop is UNKNOWN, never PASS. No retry is implied.

Before the explicit root once GO, all four methods remain NOT_RUN. Full tests,
SQL, throughput, long-duration stability and exchange acceptance are separate.
