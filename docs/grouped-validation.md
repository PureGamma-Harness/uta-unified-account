# 分组接纳的独立风险不变量验证

本验证由独立验证组编写，与 `AdmissionBatcher` 的实现、吞吐工具和存储故障验收分别开发。所有账户、资金、价格和故障均为合成数据。验证允许候选继续工程审查，**不授予生产、PM、多节点、持续万笔或真实资金启用资格**。

## 独立参考与假设

`tests/test_admission_invariants.py` 不调用生产的 `calculate_risk`、`_reserve` 或 `_admit_order` 来生成预期值。参考账使用精确 `Fraction` 维护每账户现金、各业务 ID 的原始内容、活跃预占及撤单状态，按固定的 Cross 限价政策逐命令计算。

在本组无仓位、无贷款的现金预占案例里，mark 为 100 USD，IM 率为 0.1，费率为 0.0004，USD 精度为 8。对于有符号数量 `q` 和限价 `p`，人工审查的预占为：

`|q| × max(100,p) × 0.1 + max(0,q×(p−100)) + ceil(|q|×p×0.0004×10^8)/10^8`。

同一账户的每个待成交单独占用此额度，即使方向相反也不先净额化。相同 ID、数值等价内容重试不新占额度；不同内容冲突；撤销 ID 留存，重试不重新激活。每个候选决策依据此前逻辑命令的已暂存状态，外部发布必须等待整组 COMMIT。

这是有界、固定参数的预占参考，不是完整 PM 模型或全部资产组合的数学证明。配置 Cross 与只减仓的专门案例另验证真实核心路径继续执行原有门禁。

## 可复跑案例

```sh
python -m unittest discover -s tests -p test_admission_invariants.py -v
```

| 案例 | 独立预期 |
| --- | --- |
| 种子 `872511`、160 条命令、3 账户 | 正反向数量、99/100/101 限价、重复/冲突/撤单逐项与参考结果一致；最终活跃占用、余额、可用保证金及事件数相同 |
| 两个 batcher 与同步 writer，共 18 个同时争用者 | 账户 30.12 USD，单笔预占 10.04；恰好 3 个唯一订单被接纳，其余为保证金拒绝，不能双花 |
| 同 ID 的并发等价重试、冲突和响应丢失 | 一份耐久预占及接纳事件；新实例/worker 重启后原 ID 重试无新增影响 |
| `prec=1`、Emax/Emin 为 ±2、Inexact/Rounded traps | 有效 Decimal 命令仍得到精确预占；不能因舍入放过 1e12 上限 |
| 累计只减仓数量与 `liq:` 权限 | 已有 2 单位仓位，−0.75 与 −1.25 可占，额外 −0.01 拒绝；客户不能伪造/取消清算 ID；平仓后的历史 ID 不重开 |
| 持久配置 Cross 产品目录 | spot/未知产品不能进入 perpetual 接纳；tick、step 仍强制检查；合法接纳继续使用原 rule/catalog 版本 |
| COMMIT 前暂停 | 库内已暂存订单但只读另一连接不可见；成功及已排定业务拒绝两个 Future 都未完成；COMMIT 后才发布 |
| 行情过期或暂停 | 事务内以当前状态拒绝增量风险；撤单可在同一降级环境提交，保留风险降低路径 |
| 业务写入后的策略拒绝 | 被拒命令已尝试写 order/version/event，savepoint 全部撤回；前后两个合法命令仍能提交且预占独立相加 |
| 持久风险参数损坏 | 同组撤单与新单全部技术失败；不能把参数损坏计为普通风险拒绝并提交部分结果 |

COMMIT 的观察用真实 SQLite 事务、另一个连接及可控事件门闩，不用未提交的内存结果假装持久化。18 个竞争者使用独立服务与 batcher 实例，仍共享同一 SQLite 写入权威；该案例不证明跨主机 lease、复制或旧主 fencing。

## 已复现并推动修复的错误分类

首版 `32c2014` 漏把 `margin_rule_conflict` 视为整组技术故障。合法行情发布本已拒绝与固化规则冲突的 IM/MM，因此事务中读取到这样的持久快照表示损坏/不一致，而不是本次客户订单的正常业务拒绝。

独立回归先保存合法订单，再将持久市场 IM 从 0.1 改为 0.2。在同组提交“撤原单 + 新增订单”时，旧版返回撤单成功并把新单记为 409 业务拒绝。它违反本候选对参数损坏的整组失败契约，也会污染拒绝统计。独立测试真实失败后，实现在 `e69244b` 将其归入 fatal；**未修改独立预期来迁就旧实现**。

修复后两个 Future 均返回 `admission_batch_failed`，账户版本、订单、事件、账本均保持原值，business-rejected 计数为零。技术失败应查询或按原业务 ID 重试；异常发生在 COMMIT 后或响应丢失时不能推断确定未提交。该不确定性与底层进程/磁盘/COMMIT 故障由另一个独立故障组补充验证。

2026-11-14 在独立 worktree 应用 `32c2014` 与 `e69244b` 后，本组 **10 项测试全部通过、0 skips**。早期预览 9 项通过，加入上述损坏案例后实际出现 1 个失败；修复后 10 项均绿。最终集成 SHA、完整测试与性能仍由根集成记录，不能用此小范围结果替代全仓验收。

## 审查结论与剩余门槛

当前已验证范围未发现遗留的金融预占差异或业务拒绝隔离问题。可继续 opt-in 分组接纳工程审查。需要保留边界：多个逻辑命令共用一组提交不等于客户端多订单原子指令；回执的账户/订单版本可能早于同组后来命令，客户应查询当前状态，不能把旧回执当作永远活跃的订单。

本组没有验证长期热点公平性、跨数据库原子性、任意组合风险、队列极端长期稳定性、外部执行器、签名/nonce、复制和跨 AZ 故障、正式 RPO/RTO，也没有真实金融负责人签字。单机 FIFO 与本地 WAL/FULL 的保证不得升级成生产可用性或持续 10,000/s 声明。相应生产关卡继续 **BLOCKED**。
