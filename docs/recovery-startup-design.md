# Managed startup protocol proposal for independent review

This proposal follows the [measured startup evidence](recovery-scaling.md). It is a design for independent review, not an approved implementation. The evidence established one initialization expiry, with a later replacement READY; it did not establish permanent recovery failure. Production/HA/capacity gates remain false.



Do not fix this by an unbounded TTL increase or a renewal thread around the existing constructor. `ExchangeService` performs full replay inside `BEGIN IMMEDIATE`; another connection attempting to renew the token needs the same SQLite writer lock and can remain blocked until the initializing lease has already expired.

The preferred design to review is a read-only pre-acquisition verification phase, followed by a short fenced binding check. The verifier would run the existing complete historical integrity reference in an existing-only read transaction, validate all required non-ledger projections and schema/guard definitions, and produce a private, non-public verification receipt. That receipt must bind the authority identity and canonical path, database inode/boot identity, schema and guard digests, exact verified ledger head/count, the balance projection digest, and all service/credit/audit projections that initialization trusts. A ledger head alone cannot detect changed balances, schemas or non-ledger state.

After acquiring a fresh token, the initializer must validate that binding under the writer transaction before consuming the receipt and advertising READY. An unchanged head is insufficient unless the entire bound snapshot is unchanged. If a concurrent old owner changed any bound state, fail closed and repeat verification, or use a formally specified complete tail/projection catch-up protocol; do not silently skip replay. Receipts must remain an internal capability tied to that verified snapshot, never a caller-supplied `verified=True` flag. Fresh-file creation, existing-authority fencing, immutable guards, corruption rejection and the raw-FD lock fix must remain intact.

An alternative is a formally supported initialization phase where full verification uses a consistent read-only snapshot while lease renewal uses a separate short writer transaction, with an independent progress/deadline policy and a final fenced snapshot/projection check. It still needs exact change detection, loss-of-lease cancellation and a clean ownership state transition; it cannot renew an expired generation or advertise readiness from a stale snapshot.

Either design requires an independent correctness review before runtime implementation, including corrupted old events/balances/schema, head and non-ledger changes between phases, token expiry, another owner, process death, rollback and adversarial caller receipts. Full historical verification remains the reference. No such runtime change is implemented here.

## Binding and boundedness questions that must be resolved

A proposal that computes a full projection digest before acquiring the token and recomputes the entire digest afterward merely moves another unbounded scan into the five-second lease. A ledger head, file size, mtime, `PRAGMA data_version` copied between different connections, or an arbitrary caller-supplied receipt is not a sufficient constant-time substitute. The implementation must specify why every verified financial/schema object stayed unchanged across the handoff.

One conservative first protocol to review uses the existing router gate as the continuity capability. Before verification, the supervisor completes existing registered-owner recovery. The initializer waits for any active prior lease without holding the exclusive router gate, acquires that gate, rechecks ownership is inactive, and performs full existing-only read-only verification while holding it. All supported financial paths must demonstrably hold the compatible router gate; expired former owners remain rejected by the existing transaction-end fence checks. The gate must remain held continuously through fresh lease acquisition and the short final transaction. An internal receipt can then bind the exact verified head, projections, authority/inode and schema plus the still-held gate, without pretending the head itself proves projection identity. Any loss of gate continuity, prior-owner race, identity change, unexpected schema action or uncertain write path invalidates the receipt and restarts verification.

This conservative variant can serialize shard startup and block other shard work behind the global gate. It needs an explicit availability/RTO tradeoff assessment, and it must reject or separately handle supported writers that do not participate in that gate. Replacing the gate with durable financial-generation counters would require a separately reviewed schema/guard protocol covering every relevant table and DDL operation; no such counters currently exist. Do not infer them from the ledger head.

The owned read-only verification alternative may have a cleaner handoff: acquire the existing token, hold the required router gate, verify a consistent read snapshot while an independent bounded renewal connection makes only lease-control writes, then enter the short financial writer transaction with the same still-live generation. The token prevents another valid financial writer during verification; renewal must not depend on the verifier's SQLite writer lock. This requires a cancellation/progress policy, exact handling of old in-flight transactions, validation that the read snapshot covered all trusted projections/schema, and an internal receipt that cannot be forged by service callers. A renewal thread around the current write-transaction replay does not provide this property.

The independent review should select and fully specify one protocol before implementation. It should make cold/warm replay variability, large account/credit/funding/spot histories, interrupted verification and startup concurrency part of the acceptance plan, while preserving corruption rejection and the complete historical reference verifier.
