# 本地撮合与两侧结算契约

此里程碑提供可独立运行的 **单数据库、线性 USD 合约限价撮合**。撮合读取已经持久接纳并预占保证金的订单，实际买卖订单交叉后才生成成交；标记价仅用于风控，不能凭标记价制造成交。默认手续费和保证金属于本系统的合成验收政策，未经独立审查不得解释为 Bybit、Binance 或 CME 的交易规则。

## 支持与拒绝边界

| 项目 | 本版本行为 |
| --- | --- |
| 产品与模式 | 使用 `ExchangeService` 的线性 USD 结算模型与 Cross 风险约束；产品目录启用必须另经配置门槛。不能把某个符号名称作为反向、期权或交割合约的实现依据。 |
| 订单 | 已持久接纳的限价单、部分成交、只减仓清算单。市价、条件单、改单、IOC/FOK、多腿订单未实现，不能通过本接口隐式降级。 |
| 撮合优先级 | 买单最高价优先、卖单最低价优先；同价使用本地权威插入序列排序。成交价格为较早接纳的 maker 限价。 |
| 自成交 | 同一账户的买卖单交叉时撤销较晚接纳的 taker，不产生费用、仓位或成交回执。 |
| 行情过期 | 保留待成交订单和预占；返回 `market_unavailable` 阻断原因，不产生确认成交。 |
| 全局暂停 | 普通订单不获新的执行授权。只有双侧均满足严格减仓要求时才可能成交；不会为了给清算单提供对手方而绕过普通账户暂停。 |
| 账户执行风险拒绝 | 两侧结算一起回滚，然后撤销被拒绝的一侧订单并记录原因；另一侧未成交数量和资金保持。 |
| 无对手方或不交叉 | 返回零笔成交；未成交风险仍存在，不把计划数量作为已清算数量。 |
| 外部撮合与分片 | 不接收外部已成交事实，不提供跨数据库原子结算或复制确认。 |

## 单笔成交的事务边界

`Matcher(exchange).match_once(symbol, max_matches=100)` 在 `BEGIN IMMEDIATE` 后选择买卖单，按最新可信行情重新授权两侧执行，在同一事务中写入：

1. 买侧和卖侧的唯一成交 ID、累计成交量、订单状态与账户版本。
2. 双侧仓位、成本、已实现损益、累计手续费及逐币种平衡的资金分录。
3. `uta_matches` 唯一撮合回执；回执外键指向两条已经写入的成交记录。
4. 一条全局 `MATCH_CONFIRMED` 审计事件和双侧各自的 `TRADE_CONFIRMED` 私有事件。

完成 SQLite `FULL` 同步事务提交后才返回确认回执。没有第二侧成功、回执或事件写入失败时，不允许留下单侧财务影响。正常业务拒绝通过保存点回滚两侧；意外异常使整个有界批次回滚，因此响应丢失或异常时客户端必须按撮合回执查询，而不能推断部分成功。

每个批次最多确认 `max_matches` 笔，最多尝试 `2 * max_matches + 1` 个交叉候选。未获得对手方的剩余订单留在书中。全量订单簿扫描和排序仍是单节点性能瓶颈；此限制不是万笔吞吐的证明。

## 标识符、查询与恢复

撮合 ID 由双方账户、订单、成交前累计量、实际数量及价格的规范表示计算 SHA-256。两条成交 ID 分别由同一摘要加 `:b`、`:s` 构成。重复运行先读取事务内的最新订单状态，不能重新消费已完成数量。多个撮合 worker 竞争由同一数据库写锁串行化。

`Matcher.trades(after=0, limit=100)` 按全局 `sequence` 返回不可修改的回执。`trade_id` 可以关联双方订单、双方成交、分录业务 ID、市场版本和私有事件。全局回执含双方账户身份，属于运维审计数据；私有事件只暴露当前客户自己的订单和成交 ID。

进程在 COMMIT 前终止时，未提交两侧影响一并回滚；已提交回执重启后保留。数据库恢复仍须使用同一时点的整个数据库，不能单独恢复订单或仓位表，也不能删除 WAL 来“解锁”。跨主机故障、多可用区复制、旧主 fencing 和外部执行结果未知不在此单机保证中。

## 可运行命令

先通过认证接口建立合成账户、发布新鲜行情、记入合成资金、明确解除暂停，并提交可交叉的双侧订单，然后执行：

```sh
python -m uta.matching --database /var/lib/uta/exchange.sqlite3 --symbol BTC-PERP
```

增加 `--loop --interval 0.1` 可持续轮询本地订单簿。进程本身不拉取行情，行情过期会安全阻断。数据库资产精度默认 `USD=8`，可重复指定 `--asset-scale ASSET=DIGITS`，必须与已保存定义一致。命令输出 JSON，分别列出确认成交、撤单、阻断及批次耗尽情况；进程重启后从数据库继续。

部署前先停写并执行一致备份，保存原 commit、数据摘要和软件包。此模块只新增 `uta_matching_schema`、`uta_matches` 及不可修改触发器，不重写已有资金分录。回滚程序版本前须停所有写入者，核验目标版本可以读取现有核心 schema；不能通过删除已确认撮合回执回滚交易。交易结果纠错必须以新的授权补偿分录和业务记录处理。

## 验收与规则追溯

| 规则 | 本系统政策 | 验证 |
| --- | --- | --- |
| MATCH-001 | 数值价格优先、同价权威插入序列优先、maker 价 | `MatchingTests.test_price_priority_is_numeric_not_lexical_and_time_breaks_ties` |
| MATCH-002 | 无真实双侧交叉订单则无成交 | `MatchingTests.test_uncrossed_or_one_sided_book_never_creates_mark_fills` |
| MATCH-003 | 同一账户自成交撤 taker | `MatchingTests.test_self_trade_prevention_cancels_taker_without_financial_effect` |
| MATCH-004 | 两侧、仓位、分录、回执、事件共同提交 | 第二侧风险拒绝、意外异常及回执发布失败三个回滚测试 |
| MATCH-005 | 重启及多 worker 不重复消费订单数量 | `MatchingTests.test_restart_and_competing_matchers_cannot_settle_one_trade_twice` |
| MATCH-006 | 清算只按实际确认成交减少风险，不假设流动性 | `MatchingTests.test_confirmed_partial_liquidation_survives_restart_and_reconciles_four_sides` |
| MATCH-007 | 过期行情和暂停安全阻断执行 | `MatchingTests.test_halt_and_stale_preserve_unexecuted_orders_and_margin` |

`Matcher.verify(strict=True)` 核对撮合回执、双方订单与成交、逐笔分录及审计事件；严格模式拒绝绕过双侧撮合的手工成交。完整四侧对账还必须执行 [独立仓位重放](reconciliation-spec.md) 的 `reconcile_exchange(exchange)`，以核验订单累计量、仓位数量、成本、费用及有效导入创世状态。外部源资金与写入者失效仍须额外证据。

人工可复算清算例：账户以 1,000 USD 开仓买入 90 单位、成交价 100、手续费率 0.0004，现金为 996.40。标记价降到 90 时权益为 96.40、MM 为 405。真实对手方分两次各买入 45 单位，清算账户每次实现亏损 450、手续费 1.62，最终现金 93.16、仓位为零。测试中开仓和两笔减仓均有真实双侧订单、独立成交回执和资金分录；重启后剩余未成交量保持。

本组工程验收通过不等于独立验证组上线签字。万笔持久订单检查与万笔唯一清算成交的持续容量、多节点复制、无流动性升级及保险基金/ADL 门槛均须单独验收。
