# 故障验收与恢复边界

本报告覆盖合成账户、本地文件系统、单节点 SQLite WAL/FULL 事务。它是独立故障验收的一部分，不授予真实资金上线许可。跨可用区复制、权威写入者选举、旧主 fencing、跨分片结算、托管对账和 30 分钟万笔负载尚未通过本报告验收。

## 可复跑证据

## 故障与通过条件

| 测试编号 | 故障注入 | 必须观察到的行为 | 覆盖范围 |
| --- | --- | --- | --- |
| FA-001 | 每连接设置 `PRAGMA max_page_count` 为现有页数，持续写入直至真实 `SQLITE_FULL` | API 返回 `storage_unavailable`；该命令的账户、订单、账本与事件均不变；解除上限后原 ID 可成功且只生效一次 | SQLite 数据库满的实际错误路径；没有占满共享主机磁盘 |
| FA-002 | 一个连接持有 `BEGIN IMMEDIATE`，另一个连接的 busy timeout 为 50 ms | 没有成功接纳回执；503 明确失败；释放锁后原订单 ID 可接纳一次 | 独立连接的写锁争用 |
| FA-003 | 已写资金分录及账户版本，尚未提交时 `os._exit(73)` | 重启后四类状态全部回到提交前；同业务 ID 重试不冲突、不丢账 | 未确认本地事务的进程崩溃 |
| FA-004 | 成功提交后退出，分别模拟已收到回执与响应丢失 | 重启保留已提交命令；原 ID 重试不新增分录、版本或事件 | 本地已确认命令及结果未知查询协议 |
| FA-005 | 行情超时并启用 halt | 新的本地执行拒绝且状态不变；成功命令可重放原回执；普通撤单仍成功 | 按操作类型降级，未验证外部交易所撤单 |
| FA-006 | 枚举两订单、两成交、撤单、重试与各提交阶段故障 | 安全模型 48 个可达状态保持逐币平衡、双侧对应、仓位净量及剩余占用；故意破坏原子性、幂等和逐币核算的模型给出反例 | 有界安全性，不能自动证明生产实现与模型等价 |
| FA-007 | 两侧订单已接纳；第二侧 `FILL_APPLIED` 或 `MATCH_CONFIRMED` 处直接 `os._exit` | 重启后双方资金、订单、仓位、分录、成交回执及事件全部回到撮合前；原挂单仍可完成一笔唯一成交 | 实际撮合服务、同 SQLite 事务内的进程故障 |
| FA-008 | SQLite 触发器拒绝 `uta_matches` 插入 | 两侧结算都回滚，订单保留原剩余量；移除故障后恰好一笔成交 | 回执写入失败注入；这项不是物理磁盘满测试 |
| FA-009 | 撮合提交后、发送响应前 `os._exit` | 重启查得一笔回执、两笔 fill、双方各一次费用及相反仓位；再次撮合不重复执行；逐币原始整数分录总和为零 | 双侧提交成功但结果未知的恢复路径 |

`max_page_count` 触发的是 SQLite 的真实 `SQLITE_FULL`，不是一个名为“磁盘满”的普通异常或触发器模拟。它没有覆盖操作系统级 `ENOSPC`、fsync 失败、WAL 所在设备故障、只读重挂载和数据库页损坏；这些仍需独立设备或故障文件系统演练。测试发现 SQLite 在 FULL 时可能自动回滚整个事务，账本不得再用不存在的 savepoint 覆盖原始错误；该问题已在基线修复。

## RPO、RTO 与故障模型

| 故障域 | 当前目标或观测 | 验收状态 |
| --- | --- | --- |
| 进程终止，原本地磁盘及 WAL 保留 | 在 SQLite WAL/FULL 正确落盘、设备履行 fsync 的假设下，已成功确认命令目标 RPO=0；测试样本丢失 0 | 小样本通过；不外推到硬件断电 |
| 进程恢复 | 上表只测毫秒级小夹具启动；尚未测大账本重放、完整恢复与流量恢复 | 服务 RTO 未定义、未验收 |
| 节点磁盘永久丢失 | 只能恢复到经校验备份的水位；备份后的幂等键和业务状态需要外部证据追账 | RPO 取决于实际备份间隔，未验收 |
| 可用区丢失、跨区复制落后 | 当前没有复制确认、选主或 fencing 机制 | BLOCKED |
| 旧主与恢复副本同时接单 | 当前部署必须由管理员停止旧写入者，不能自动防止两份数据库并行成为权威 | BLOCKED |
| 外部撮合已执行但本地不确定 | `apply_fill` 是本地执行授权与结算，不是不可撤销外部成交事实摄入器 | 适配器、查询和对账机制未验收 |

## 处置与回滚

1. 数据库满、忙或不可用时停止新增风险并保留失败命令 ID。调用方不得换一个 ID 重发结果未知命令；应先恢复存储，再用原 ID 重试或按原业务引用核对回执及事件。
2. 禁止通过删除 WAL、复制运行中的主数据库文件或清空幂等记录恢复服务。先停止全部写入者，保留数据库、WAL、日志及客户端成功回执的取证副本。
3. 存储空间恢复或进程重启后，使用相同资产精度和规则配置打开服务，运行账本独立回放校验，核对客户余额、订单状态、预占、仓位和消费水位。再提供新鲜行情，核对 halt 与账户冻结状态。
4. 若需从备份恢复，按 [部署与恢复手册](operations.md) 恢复到新路径。只有完成备份之后已确认命令、外部托管资金及执行结果的追账，才可恢复接单；不能用回退数据库抵消已经确认的成交。
5. 资金纠错须新增可审计冲正或补偿业务，而不是修改原始流水。本报告不批准未经核对的自动冲正、人工解除破产账户或对真实账户批量重放。

## 模型假设

`formal/explore_settlement.py` 不导入生产代码。它抽象两笔各一单位成交、两侧订单、两种资产、单一事务写入者与唯一成交 ID。买侧、卖侧和成交回执先进入事务内暂存，只有一个原子提交可以让它们同时可见；任何暂存阶段崩溃都丢弃整个暂存状态。撤单不能穿越持有写锁的事务，已确认成交的重试不能再次消费剩余量。

安全性质包括每个成交恰好一个买侧、一个卖侧和一个回执，合约净量为零，分录逐币平衡，以及仅未成交且未撤销的数量保留占用。故意的单侧先发布、无幂等重试和跨币种总额抵销会产生反例。模型不证明公平性、最终成交、行情与保证金正确性、价格时间优先、复制协议、外部副作用恰好一次或无限规模系统。

FA-007 至 FA-009 已在实际本地撮合模块完成，不使用按标记价直接生成的成交模型。验收直接查询订单、fill、仓位及原始整数分录，同时调用撮合对账器复核回执；没有对手挂单时不会制造成交。它们关闭本机原子提交的相应小样本功能门槛；完整生产容量、跨节点恢复和独立生产审核仍是未关闭门槛。
