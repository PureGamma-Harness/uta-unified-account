# PM 吞吐与极端行情压测

万笔每秒是端到端验收目标。风险计算、订单写入、清算成交和账户处置各有不同的完成条件，应单独计数。比如一次清算调用可能只撤单，也可能产生多笔成交。只有已生成清算成交、提交账户快照和资金分录的动作才计入成交吞吐。

调用与分片提交边界见 [事务架构](architecture.md)，撤单和成交的具体分支见 [清算流程](workflows.md)。本页数据由 [benchmark_pm.py](../scripts/benchmark_pm.py) 生成：计算、单命令延迟、整个账户生命周期和批次延迟是不同计时对象，不能直接用其中一个替代另一个。

## 复现

在仓库根目录使用 Python 3.10+。通过 `--db-dir` 选择实际承载 SQLite 文件的存储位置，避免把临时内存文件系统的结果用于估算磁盘性能。退出后，压测会删除创建的临时库。

```bash
python scripts/benchmark_pm.py --mode compute --workers 8 --checks-per-worker 20000
python scripts/benchmark_pm.py --mode all --workers 4 --checks-per-worker 3000 --accounts-per-worker 80 --db-dir .
python scripts/benchmark_pm.py --mode durable --workers 4 --shards 1 --accounts-per-worker 80 --db-dir .
python scripts/benchmark_pm.py --mode durable --workers 4 --accounts-per-worker 100 --db-dir . --target-rate 10000 --max-pending 8
python scripts/benchmark_pm.py --mode batch --workers 4 --accounts-per-worker 80 --batch-size 32 --db-dir .
python scripts/benchmark_pm.py --mode batch --fused --workers 4 --shards 4 --accounts-per-worker 80 --batch-size 32 --db-dir .
```

- **PM 计算**使用 17 组模拟账户和 61 组行情水平，包含 BTC、ETH 多空、抵押品、负债及相对开仓价下跌 60% 的价格。每次计算完整的六场景风险报告，并判断一笔模拟订单的保证金。模型参数和账户对象提前构造，计时包含场景计算及保守保证金检查，排除 HTTP、JSON、存储和进程启动。
- **持久化下单**提前建户，多进程同时发起真实模拟器命令。四分之三的请求应提交订单，其余应因初始保证金不足而拒绝。校验提交或拒绝的版本和事件，并重新打开数据库对照状态。
- **持久化清算**为每个账户构造多头仓位和挂单，测量合成市场下跌 45% 后的行情更新、保证金检查、撤单和实际模拟清算成交。逐账户核对仓位不得反向或扩大、成交分录收支相抵、事件版本连续、挂单均撤销。可保留平仓后的负债。压测把完整处理过程和仅执行清算命令的延迟分别报告。
- **清算组提交**将同一批账户分三轮提交行情、撤单和清算成交。每组按账户分片写入，延迟按批计，不与逐命令延迟直接比较。
- **合并清算命令**在每个账户的同一命令内完成行情更新、撤单和模拟减仓，再由分片组提交。计时包括成交后状态与审计读取。
- **并发与存储**以进程数作为并行度，`--shards` 控制各进程使用多少个 SQLite 文件。各进程共享 SQLite 路由，按固定哈希把账户分配给数据库文件。使用同步启动，账户准备和最终重开数据库验证在计时区间外。默认每个进程完成当次请求后开始下一次。指定 `--target-rate` 后，调用方按计划到达时间模拟请求排队，每进程队列最多保留 `--max-pending` 个等待账户，超出部分计入过载拒绝。已处理账户的额外延迟从计划到达开始计时。
- 统计从首个进程开始到最后一个进程结束的总吞吐。P50、P95、P99 来自各进程的全部请求耗时，以 nearest-rank 算法计算。预期的风险拒绝有独立计数，过载拒绝和未完成账户另外统计，偏离预设处理结果或重新打开后数据不一致将作为技术错误报告。

## 本地基线

Linux x86-64，Intel Xeon Platinum 8573C，容器可见 9 个逻辑 CPU，Python 3.12.14，SQLite 3.53.1。写入使用当前工作目录的 overlay 文件系统，各账户库用 WAL，并以 `synchronous=FULL` 提交。本表为单次测量，并非运行承诺。

| --- | ---: | --- | ---: | --- |
| 六场景 PM 计算与订单保证金判断 | 160,000 次 | 8 进程 | 10,809.43 检查 | 0.616 / 0.947 / 1.338 ms |
| 持久化订单检查 | 320 次 | 4 进程，4 库 | 624.89 检查，468.67 提交 | 3.968 / 12.618 / 38.035 ms |
| 持久化清算 | 320 户，640 条清算命令 | 4 进程，4 库 | 108.50 成交，217.00 命令 | 6.584 / 14.452 / 39.415 ms，按命令 |
| 持久化清算 | 320 户，640 条清算命令 | 4 进程，1 库 | 80.75 成交，161.51 命令 | 5.263 / 36.514 / 132.728 ms，按命令 |
| 持久化清算组提交 | 320 户，640 条清算命令 | 4 进程，4 库，批大小 32 | 200.52 成交，401.05 命令 | 92.806 / 107.844 / 107.844 ms，按成交批 |

计算运行 14.802 秒。160,000 次检查中预期风险拒绝 20,990 次，技术错误为零。订单检查的 320 个账户产生 240 个提交和 80 个预期拒绝。逐条写入和组提交的各组测试分别将 320 个受影响账户的仓位全部清至零，记录残余债务并重新打开状态复核。4 库与 1 库的账户处置 P99 分别为 84.766 ms 和 283.591 ms，包含行情更新、撤单、成交、状态读回及在线对账。账户构造时使用合成价格，尚无真实盘口冲击、停牌、丢包、共识提交或跨主机故障数据。

这些清算结果的原始计数含 `end_health_INSOLVENT=320`：仓位处置完成后仍保留负债，完成吞吐不等于恢复偿付能力。逐条清算的 `verified_account_lifecycle` 包含计时内的状态和事件核对，计时后的 `reopened_accounts_verified` 只确认重开的快照、版本及仓位；完整的逐回执重算由独立 `replay`/情景检查完成。技术错误为零也不表示没有业务拒绝或过载。

以 10,000 户每秒的速率在 40 ms 内模拟 400 户同时等待清算，4 库配置完成了 40 户及其清算成交，360 户触发压测客户端的队列上限。已完成账户从计划到达时刻计算的 P99 为 304.261 ms，包含排队。该结果测量的是有限本地突发，端到端的服务背压、撮合网络和持续请求造成的积压仍需独立验收。

原始结果见 [计算](benchmarks/compute-eight-workers.json)、[4 库 WAL](benchmarks/wal-four-shards.json)、[单库 WAL](benchmarks/wal-single-file.json)、[定速突发](benchmarks/paced-overload.json)、[清算组提交](benchmarks/wal-group-commit.json)和[合并清算命令](benchmarks/wal-fused-liquidation.json)。12 批的小样本中，合并命令提升了总体吞吐，尾延迟仍高，320 个账户均完成并重开核对。

## 扩容与验收

1. **确定账户所有权及背压。** 以账户为路由键交给固定分片，账户内使用有界命令队列串行处理。新单与清算共享一致的账户版本。行情高频刷新使用只读行情快照和版本，而不是为每次快照覆盖所有账户。背压触发时拒绝增加风险的订单，为撤单、只减仓和清算保留容量。迁移分片前确认旧持有者失去写权限。
2. **统一风险输入并复算。** 用版本化行情及风险参数预计算各产品的场景冲击系数，维护账户的场景敞口。若采用定点数或向量化计算，保留当前精确有理数模型做差分。比较阈值附近的接单和清算决策，并记录溢出、舍入方向和无一致快照时的拒绝。
3. **限制写放大。** 把账户版本、保证金预留、过账和命令回执写入同一个事务。本地组提交按分片提交单个命令的账务和回执。生产部署可评估追加日志、组提交等待预算和多副本确认，每个回执应在持久提交成功后发出。快照可定期生成，启动后按分片顺序重放，检测序号缺口和重复命令。
4. **区分清算决定和实际完成。** 接入撮合后，按行情版本和可成交数量生成只减仓指令，绑定稳定的动作 ID。成交、撤单回执丢失时先查询或重放真实结果，再继续推进状态。清算完成率按结果提交计，撤单、部分成交、重试、保险处理均单独记录。
5. **用开放负载验收。** 在目标配置上持续按设定速率提交请求，计时以计划发送时刻为起点，覆盖排队延迟，避免遗漏服务降速时本应到达的请求。分别验证端到端订单检查及接单提交、端到端清算成交提交、混合流量。建议初始验收运行连续 30 分钟，目标每条链路至少完成 10,000 笔/秒；另测试叠加两倍突发、热账户偏斜、行情扇出、分片重启和结果重放。记录机器、存储和数据集、客户端积压、P50/P95/P99、版本冲突、技术拒绝、有效业务拒绝、资金对账，以及欠账和数据丢失情况。当前仓库的基准尚未执行该验收。
