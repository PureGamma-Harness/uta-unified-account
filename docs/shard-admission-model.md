# 分片接纳调度、行情屏障与崩溃重试的有界模型

本模型由独立协议验收组编写，源码为 [formal/explore_shard_admission.py](../formal/explore_shard_admission.py)，从仓库基线 `92086bd` 单独实现。它只使用 Python 标准库，不导入 `RouterAdmissionBatcher`、`ShardRouter`、数据库或风险计算代码，不把生产实现的输出当作正确性判断。

模型是有限状态安全检查，不是实现等价、模型组合、TLA+、HA、活性或金融公式的证明。即使枚举全部通过，仍需实际 SQLite 故障测试、跨进程屏障测试、回放对账和独立容量验收。

## 调度与行情屏障模型

固定两个分片、两个 worker、两个账户和三个订单命令。`alice` 的两个命令按顺序进入片 0；`bob` 的一个命令进入片 1。每个命令对应一个固定、唯一的业务 ID 和一个单位的预占。

队列选择最早的可运行分片，再选择该分片非空的队列前缀，组大小为 1 或 2。同一分片只允许一个 active group；它一直占用调度所有权至已提交结果交付完成。不同分片可以任意交错完成，不定义全局完成顺序。分组大小刻意允许任意合法前缀，作为收集等待的保守抽象；没有模拟真实时间、动态 enqueue、`max_delay_ms` 或某个固定配置的精确收集路径。

每组依次经历：

1. 从队列取出并占用分片。
2. 获取共享市场屏障与片内写入权限，读取当时的 generation 和暂停状态。
3. 按组内 FIFO 执行命令并暂存预占。暂停期间只产生拒绝结果，不建立新的资金占用。
4. 一个原子 COMMIT 使该组的新预占和提交事实同时持久可见，然后释放共享屏障。
5. 交付该组的成功或拒绝结果，再释放分片调度所有权。

行情发布者只执行一轮 generation 0 到 1 的更新。它请求排他屏障并等待所有共享持有者离开；获得排他权限后先保持暂停，再依次向两片扇出新 generation。全部完成后更新全局 barrier 并释放排他权限，仍保持暂停。独立的显式激活动作再次取得排他权限，验证两片 generation 完整一致后才解除暂停。

这里允许请求排他屏障之后仍有新共享持有者获得权限，直到排他权限实际取得。模型不假设 flock 提供写者优先或饥饿自由，也不把“请求暂停”当作“暂停已确认”。

检查的不变量：

| 不变量 | 检查内容 |
| --- | --- |
| 同片调度所有权 | 一个 adapter 内，同一分片最多存在一个 active group，至多一个片内事务写者 |
| 账户 FIFO | 每个账户的已执行命令序列必须是该账户 enqueue 序列的前缀 |
| 共享与排他互斥 | 排他发布或激活不能与共享接纳屏障、未提交的接纳写者重叠 |
| 提交先于成功回执 | 每个成功命令都必须具有该组的 COMMIT 事实及一个持久预占 |
| generation 一致 | 新预占不能在 generation 已变化或已暂停、正在扇出的条件下提交 |
| 无重复调度 | 每个命令恰好在待处理、某一 active group 或已交付集合之一 |
| 无重复预占 | 单业务 ID 的持久预占只能为 0 或 1 |
| 完整激活 | 只有两片均匹配全局 generation、且不在 publishing 状态时才可开放新风险 |

“同片调度所有权”比“SQLite 只有一个实际写锁持有者”更强。移除 active-shard 守卫的变体首先展示调度协议被破坏；它不声称 SQLite 因此一定允许两个物理写事务同时提交。

## 崩溃重试模型

另一个独立模型使用一个分片、一个原始业务 ID 和至多两次尝试。每次尝试有独立的运行状态和 Future，但都查询同一个不可变业务 ID。它区分未提交暂存、成功 COMMIT、已观察成功以及提交后响应丢失。

提交前退出或 COMMIT 失败会丢弃暂存。提交后退出、响应丢失或客户端已收到成功，都保留原始持久预占；重试查回该 ID 的既有回执，不新增预占。模型额外保存一个只在成功 COMMIT 事件更新的独立 witness，用来发现失败路径泄漏资金状态。

检查以下性质：

- 资金状态始终与成功原子提交的 witness 一致。
- 相同业务 ID 重试不会产生第二次预占。
- 本次尝试的 Future 不会在本次事务提交之前成功。
- 客户端已经观察到的成功在模型规定的进程重启后仍有一个预占。

该模型以原子且持久的 COMMIT 为假设，不验证 SQLite、操作系统或存储设备是否实现了这一假设。它没有持久化队列，也没有声称重启能恢复丢失的 Future；调用方仍须按原始业务 ID 查询或重试。

## 不安全变体与反例

| 变体 | 最短反例摘要 |
| --- | --- |
| 同片 group 重叠 | worker 0 取 `alice` 首单，worker 1 忽略 active shard 又取同账户次单 |
| FIFO 超越 | 首先选择 `alice` 次单并执行，历史不再是 enqueue 顺序的前缀 |
| COMMIT 前发布 Future | 取单、获取共享权限、暂存后直接宣告成功，尚无提交事实 |
| COMMIT 前释放共享权限 | 未提交的接纳组放弃共享锁，排他发布者进入，越过应保护的事务边界 |
| 重试再次预占 | 首次已提交、响应丢失后，同 ID 再次累加预占并提交 |
| 重试 Future 提前成功 | 未提交的尝试返回成功，事务尚无 COMMIT witness |
| 回滚泄漏 | COMMIT 失败，却保留暂存的预占，与提交 witness 不符 |
| 重启丢失已确认提交 | 客户端已经看到成功，错误恢复把持久预占归零 |

这些是刻意修改抽象协议的反例，不是对运行时代码存在对应漏洞的指控。模型不会证明一个变体在某一实际 SQLite 调度下必然发生；例如共享锁提前释放后，SQLite 自身仍可能阻塞发布者的片内写入，但接纳与发布的保护边界已经不满足该模型契约。

## 对运行时的只读交叉审查

审查对象为 `RouterAdmissionBatcher._take_batch/_run/_commit_batch`，以及 `ShardRouter._gate/_admit_order_batch`。正常锁顺序为：短暂持有 scheduler condition 取组，释放 condition，再取得 router 共享 flock，读取控制与资金来源 registry，进入选中分片的 `BEGIN IMMEDIATE`，提交后释放共享屏障，最后交付 Future。收集等待不持有数据库或 router 屏障。

组内资金来源检查只使用当前分片事务及全局只读 registry，不在持有某一片写锁时再向其他分片索取写锁。这样避免两个片内 worker 各持一片写锁、再相互请求对方写锁的环。检测到完整性错误时，运行时应先退出片内事务及共享屏障，再进入排他暂停路径，避免原地升级共享锁造成自等待。

在这一正常路径中未发现已确认的锁环。回调在提交并释放共享屏障后运行，同池递归提交、关闭及等待未完成 Future 有显式拒绝。回调仍须非阻塞；模型不证明任意用户回调、跨池依赖或外部锁的无死锁性，也不证明等待时间上界。

异常分类必须由实际故障测试另行验收：市场与预期业务拒绝只能回滚自己的 SAVEPOINT，SQL、存储、配置及完整性故障必须使整组失败；被包装的存储异常不能因为外层状态码看似业务拒绝就被忽略。本模型没有调用或复制运行时的错误 allowlist。

本轮交叉审查提出了 `router_halted` 特殊分支绕过统一 cause 检查的边界。实现组在 `253d518` 将该状态加入统一分类入口，继续执行被包装 SQLite/Ledger/Storage 原因的致命检查，并用真实 SQLite 缺表异常包装成 `router_halted` 503 验证整组回滚。该运行时测试与修复是独立证据，不是有界模型覆盖了 SAVEPOINT 异常语义。

## 不能从通过结果推导的结论

两个模型没有共享一个合成状态空间，未给出模型组合证明。调度模型没有进程重启；重试模型没有多 worker 或跨片调度。因此不宣称跨重启、多个 adapter、同步调用者或多个主机之间的全局账户 FIFO。实际文档只承诺单 adapter 的 enqueue 顺序，实际 SQLite 负责其他合作调用者的事务序列化。

还未覆盖动态生产者、队列过载及取消预留容量、pending Future 取消、SAVEPOINT 分类、任意业务参数、真实价格时效、精确风险计算、撮合、跨片成交、任意次重试、线程故障、任意规模状态、HA、复制、旧主 fencing 和真实硬件断电。模型不设置公平性，不证明无饥饿、最终完成或容量目标。

协议变更后必须重新跑模型、保留 JSON 反例及结果，再结合与该代码提交对应的实际故障验收。通过本模型不能代替生产审批，也不能把短测吞吐或局部计算吞吐升级为交易系统万笔端到端能力。
