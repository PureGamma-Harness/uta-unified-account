# 单机分片实验的独立故障审查

本审查由独立故障验收工作组执行，覆盖 PR2 的单机 `ShardRouter` 实验。它不批准生产启用、跨分片撮合、跨区复制、自动选主或真实资金迁移。审查基线为 M1 `ec5fee9`，叠加分片实现 `f3ab8d8`、真实 router 基准 `1a2beb9`、结果归档 `9240d84` 和身份保护 `f62ad25`。

## 发现与处置要求

| 编号 | 复现及影响 | 必须满足的拒绝行为 |
| --- | --- | --- |
| SF-001 | 保存旧控制库；经 router 将凭证 P 的 10 USD 记入片 0；离线恢复旧控制库但保留较新的分片；新 router 可把同一 P 再记入片 1。两个池各得到 10 USD | 启动对账本地已入账资金来源与全局 claim。缺失、内容不符或跨片重复均返回 `funding_registry_conflict` 503，并持久全局暂停；不得自动丢弃或改派来源 |
| SF-002 | 已运行的 router 中，用片 0 的有效数据库替换片 1；原身份校验仅在构造时执行，旧对象仍能在错误数据库中创建路由到片 1 的账户 | 每个分片事务在写入前检查不可变片号及 layout；不匹配返回 `shard_identity_conflict` 503，不能修改账户或分录 |
| SF-003 | 已运行的 router 的分片文件被删除；基础 Database 会重新创建空 SQLite 文件，最后只报表不存在 | 在打开及建库前拒绝缺失或空文件；返回 `shard_unavailable` 503；不得以空库替代丢失的金融状态 |
| SF-004 | 已激活后模拟单片额外行情；再次激活虽检测到 `market_barrier_mismatch`，但原全局 active flag 保留，之后 router 仍授权新单 | 验证激活条件前先持久全局暂停；发现市场 generation、摘要或时效错误后保持暂停，后续新风险返回 `router_halted` |

SF-001 的混合恢复本来就被部署手册禁止，SF-002/003 属于运行中恢复误操作或文件损坏，SF-004 最初使用了明确不在协议保证内的直接分片写者。这些测试检查发现错误后的防御性拒绝，不能据此声称 router 能约束任意直接写入者。正常运行假设仍是所有账户业务命令只经 router，目录由可信服务用户控制，全部数据库位于同一受支持的本地文件系统。

前三项在原基线实际复现；SF-004 也已复现为“激活返回错误后，global `halted=false`，随后新单仍成功”。实现组在 `763d6c0` 修复四项问题：每事务身份及初始化封印、缺片拒绝自动建库、资金来源 registry 对账，以及在激活检查之前持久暂停。独立组将该提交应用到自己的 worktree，重新执行全部回归；未修改独立预期以迁就实现。

## 独立验收

```sh
git rev-parse HEAD
python -m unittest discover -s tests -p test_sharding_faults.py -v
python -m unittest discover -s tests -p test_sharding.py -v
```

`test_sharding_faults.py` 使用合成数据和临时目录，实际创建两个本地分片、启动独立 Python 子进程并在指定持久化边界执行 `os._exit`。没有使用线程异常代替所有崩溃场景，也没有把各片本地 flag 当作全局屏障。

2026-11-14 复测结果：10 项独立分片故障测试、12 项分片模块测试及 7 项基准工具测试全部通过。前两类合计 22 项用时约 1.7 秒，基准工具测试约 2.2 秒；这些执行时间只说明小样本测试已运行，不是系统延迟或吞吐指标。修复后没有重跑历史 1/2/4 片容量探针。

| 验收项 | 通过条件 |
| --- | --- |
| 运行中换片、缺片 | 业务写入前拒绝，缺失文件不自动重建 |
| 控制库与分片恢复点不一致 | 检出已入账来源没有正确 global claim，启动停止并保留账本 |
| global claim 已提交、片内尚未入账时退出 | 重启保留原片、原命令、原金额归属；其他片及新命令拒绝；原命令可完成一次 |
| 片内资金已提交、响应前退出 | 重启不释放 claim，不重复池资金；原命令返回幂等回执 |
| 行情扇出一片后退出 | 新旧 router 都拒绝新增风险；半 generation 不可激活；更高完整 generation 发布后仍需显式激活 |
| 激活一片后退出 | 即使片 0 本地已 ready，全局仍暂停；新旧 router 均不能绕过 |
| 初始 layout 与部分分片创建后退出 | 不能自动创建缺失片或悄悄补齐半初始化金融库；需显式人工恢复 |
| 已检测行情摘要或版本不一致 | 返回错误之前已持久暂停，后续 router 新单拒绝 |
| 双进程在途准入与暂停竞争 | admission 持共享 flock 时，另一进程的独占 halt 等待；在途命令先完成，随后 halt 确认；再来的准入拒绝 |

资金来源是多库协议：先持久 global claim，再完成某一片的本地入账，二者不是一个数据库原子事务。`claim 存在而本地没有入账` 是允许恢复的 pending 状态，必须永久绑定原命令；`本地已入账但 claim 缺失或内容不同` 是不一致状态，不能自动猜测资金权威。

## 恢复限制与上线否决项

- 控制库、来源 registry、全部分片及其 WAL 必须来自同一受控恢复点。全局暂停并停止所有合作写者后再备份；一次成功的局部恢复不构成完整系统恢复。
- 回退所有副本到更旧时点，可能同时丢失来源 claim 和片内历史；内部相互一致不等于没有丢失客户已确认命令。必须凭外部回执及托管资金记录追账，不能重新把旧凭证当作新资金。
- 同主机 flock 只协调合作进程。它没有跨主机租约、复制确认、fencing token、网络分区处理或旧主自动失效协议。不能给出跨可用区 RPO=0 或生产 RTO。
- 账户仍固定在一片；不同片的对手单不会成交。不存在跨片两侧提交、全局价格时间优先、全局共享信用池或在线 resharding。
- 历史 1/2/4 片短测约为 354/432/555 笔持久接纳每秒，容量 gates 均失败。新增事务身份校验及启动对账会改变成本，旧结果只能归属原提交，不能替代修复后的复测。
- 30 分钟持续 10,000 条持久订单接纳、10,000 笔真实清算成交、混合负载尾延迟、热点压力、长期稳定性及外部安全审查仍未通过。

独立组同意将修复后的实现作为受限实验 PR 继续审查。上述四项已确认缺陷在该代码版本的回归中关闭；任何真实资金或生产容量启用仍被否决，不能用 unit tests 通过替代上线审批。
